# Update runs

**Scope:** how several mods are updated at once, and one mod in the same way, as a run that goes on in the background: its phases, the surfaces that show it, what it asks and what it does without asking, how many things happen at once and why, what Undo, Skip, Try again and Remove from the list mean, and what is built from what.
What an update does to a folder is [`applying-updates.md`](applying-updates.md), whose mechanism a run uses unchanged. How an archive is fetched and queued is [`downloads.md`](downloads.md), and what the notification stack is is [`notifications.md`](notifications.md).

**Update N runs as described here; part of the note is still the design.** The engine (its jobs in the queue, the lanes and the host's drain), the surfaces and the questions are built: Update N starts a run, the run asks the archive's password, which of the archive's folders is the mod (the folders window), what a download shaped like a patch should do (the patch window) and whether to update over a patch nothing records, each answered from the row, the Downloads panel or the Needs you card, and the Updates page's rows, the Downloads panel, the sidebar badge and the cards show it ([§11](#11-architecture)). What is not built yet is named where it is described and listed in [§12](#12-the-slices): Undo and the finished row's detail, one mod and Reinstall as a run of one, and Cancel all, Try again, Continue and the space warning on screen. Cancel is on screen only as the Downloads panel's own controls, Cancel and Remove from queue on the rows of jobs the queue can stop, not as the Updates row's Cancel the design draws.
The picture is the board "Updating mods" (`design/v3/boards/UpdateRunToasts.dc.html`, `design/v3/renders/UpdateRunToasts*.png`); where this note and the board differ, §2, §5 and §10 say which wins and why.
[§14](#14-decisions-settled-and-decisions-not-yet-confirmed) lists what the user decided and what is only recommended, and [§13](#13-what-changes-in-the-docs-and-rules-when-the-code-lands) lists what this note replaces in the docs and rules that describe the built behaviour.

## 1. What a run is

A run is the set of download jobs that one press of Update N, or one mod's Update or Reinstall, puts in the download queue. It has no object of its own: the jobs are the run, and every surface reads the jobs.
There is no modal window anywhere in it. Pressing Update N closes the list, and the work shows on the Updates page's rows, in the Downloads panel, on the sidebar's Downloads badge and as notification cards, and goes on while the user moves between pages or leaves the app alone.

The queue already has what a run needs: a Downloads panel with Needs your attention, In progress and Finished groups, a badge, a deck of Working cards, an `updating` state, a `waiting` state that holds an unpacked archive and frees the install slot, and the split of an install into prepare, answer and finish ([`downloads.md`](downloads.md) §8, §10). A run is a second user of that split.

A run does not start by itself. It starts from a press, with the user's picks, which makes it an update the user is present for in the sense that matters: the user chose each mod and each file, and read the footer that says what an update does ([§3](#3-consent)). Updating with nobody having asked stays refused ([`applying-updates.md`](applying-updates.md) §7).

A layer of a mod (a base, or a patch on top of it) is in at most one job of a run at a time, and a job writes one or more folders:

- **One mod, one file:** the ordinary job.
- **Mods that share an archive** (the picks have the same GameBanana file id): one job with one download, one unpack and one write per folder, in order. Two transfers of one file would share a `.part` and corrupt it, so they cannot be two jobs ([`downloads.md`](downloads.md) §7).
- **A base and a patch of one folder** in one press: two jobs, one per layer, and the second does not start its write until the first has ended, since both write the same folder. A folder has one write pipeline at a time.

## 2. The phases, and what each means in the app

The board draws six phases. The app has real steps behind each, and where the board shows more precision than the app has, the app wins.

| Phase on the board | Job state | What is happening | What is shown |
|---|---|---|---|
| Waiting | `queued` | The job is in line for a download slot, or held back by the lookahead cap ([§4.1](#41-the-model)). | "Waiting to update" on the row. On the panel "<size> · downloads next" for the first in line and "N ahead of it" for the rest. No bar. |
| Downloading | `running` | Bytes are arriving, with a real rate from a 5 second window. | A mini bar, "Downloading", "79 of 233 MB · 4.1 MB/s". The rate is empty for the first second, so the row reads "Connecting..." until the estimator has a figure. The rate is per job. |
| Unpacking | `downloaded`, then `updating` with the step `unpacking` | Two steps in a row that report no progress: the unpack (listing, space check, `7z` or zip, md5) and the preview (the folder it goes into and the archive's folders are read, the layout is replayed, the patch scan runs). | An indeterminate state and "Checking what is in the file". Not a bar: one that pretended to know how far along it is would be worse than not saying ([`downloads.md`](downloads.md) §9). |
| Needs you | `waiting` | The prepare found something only the user can answer ([§6](#6-questions)). The job holds its unpacked folders and has left the unpack and install lanes. | "Needs you" with Answer. |
| Installing | `updating` with the step `writing` | The write: the mod is turned off if it was on, the old folder is saved as a snapshot, everything but the sidecar is deleted, the new files are copied, a recorded patch is put back, the new origin is recorded, the mod is turned on again if it was on, and old snapshots are pruned. | A sweep, not a percentage. Under it the sub-step that is true: "saving the old file as a snapshot", "replacing the files", and "linking it in" only for a mod that was on. |
| Updated, Patch added | `done` with the outcome `updated` or `patchAdded` | The write ended. | "Updated" or "Patch added", with Undo while Undo is offered ([§8](#8-undo)). |

**The write has no progress, and the percentage on the board's "Installing" is a simulation.** The write is one call that copies a folder and reports nothing until it ends. The sub-steps come from one small additive callback on the applier, called as it passes the snapshot, the clear-and-copy and the reactivation; the bar is a sweep that stays a sweep while the steps change under it.
"Linking it in" is drawn only for a mod that was on: a mod that was off has nothing to link, and a line naming a step that did not happen is a false line. The board shows the step for every mod, including one that is off, because its demo steps follow the percentage; that is a simplification of the board, and the app's rule wins.

**Unpacking is one state on the board and two real steps.** The row says one thing for both, "Checking what is in the file", where the one-mod update's wait modal says each ("Unpacking the download.", then "Checking what this changes in the mod folder."); no row ever claims which of the two it is in.

A job's states are the queue's existing ones: `queued`, `running`, `paused`, `downloaded`, `waiting`, `installing`, `updating`, `done` and `failed`. An update job uses `queued`, `running`, `downloaded`, `waiting`, `updating`, `done` and `failed`; `installing` is a Browse install's state. **An update job is not pausable in the first build**: the queue's `pausable` is false for a job whose intent is `callerHandles` or `update`, and Pause is not offered on an update row. The outcome of a finished job has `patchAdded`, `skipped` and `undone`, since a skipped update and an undone one stay in the list as rows ([§9](#9-what-stays-in-the-list)).
Between the unpack and the write, an update job is `updating` with the step `unpacked`: unpacked and previewed, waiting for the install lane. The row says "Checking what is in the file" for it, as for `unpacking` and for an archive landed and not yet unpacked. The write's sub-step is on the job (`DownloadJob.writing`, the mod it is writing and the step), reported by the write stage through `DownloadQueue.reportWriteStep`, and the Updates row shows it only on the mod being written.

## 3. Consent

**A run applies each update without asking about it first.** Pressing Update N, the file the user picked for each mod and the footer text are the consent. This is decided ([§14](#14-decisions-settled-and-decisions-not-yet-confirmed)): it replaces the per-mod confirmation window that precedes every write today.

What the confirmation window said does not disappear. It goes to one of three places:

| What the confirmation said | Where it goes | Does the run stop and ask? |
|---|---|---|
| The layout is unknown (nothing is recorded about how the mod was installed and the archive has more than one folder) or changed (something is recorded and the archive no longer matches it). | The folders question ([§6](#6-questions)). | **Yes.** The write cannot proceed without the answer. |
| The archive expands to no folders. | A failed row ([§10](#10-states-the-board-does-not-draw)). | No. It is a failure, not a question: there is nothing to pick. |
| The download is shaped like a patch. | The patch question. | **Yes.** A patch written by the wipe leaves a folder holding only the patch ([§6](#6-questions)). |
| A patch is in this folder and nothing records which files are its, so the wipe takes it. | A small question: update anyway (the saved copy keeps it) or skip. | **Yes.** It is the one loss no rule pays for, and the folder looks complete afterwards. |
| The archive is locked. | The password question. | **Yes.** |
| The snapshot, "everything in the folder is replaced", the hand edits and the keys the user rebound that the author's `.ini` replaces. | The footer of the Update N list and of the one-mod Update window: "Each update keeps the file you have now as a snapshot, then replaces the folder's contents", and a second sentence saying that hand edits and rebound keys are replaced by the author's. The Reinstall card says the same for Reinstall ([`applying-updates.md`](applying-updates.md) §6). | No. The press is the consent, as it is for Reinstall. |
| Folders of the archive the write leaves out ("the archive also contains X, which won't be installed"). | A line on the finished row. | No. |
| The members of a sibling group, with their cautions and refusals. | See [§9](#9-what-stays-in-the-list). | No. |
| After the write: files written, files dropped, hotkeys that changed, the mod left off because another was turned on. | Lines on the finished row ([§5](#5-the-surfaces)). | No. |
| "The old version is the way back". | Undo on the finished row, and the History tab. | No. |

**Why this is acceptable where it was not.** The argument against unattended writes is that none of the accepted losses announce themselves, and a recovery nobody knows to reach for is not a substitute for having seen the change ([`applying-updates.md`](applying-updates.md) §7). A run answers that in three ways. Every case that can hurt a folder in a way the snapshot does not announce still stops and asks. The two facts that were learned only from the confirmation, the rebound keys and the dropped files, are shown on the finished row, where the user finds out before the game. And Undo sits on that row.
It is still the user's act: the user pressed a button that names the number of mods, picked a file for each, and the snapshot is unconditional. Automatic updating, with no press, stays refused.

**A run the user does not watch needs safeguards the attended path got from the user's presence.** Those are listed in [§4.4](#44-what-must-be-true-before-a-run-goes-unwatched), and the run does not ship before they are built.

## 4. How many things happen at once

### 4.1 The model

A run is a pipeline of four stages, and each stage has its own limit, held as a constant in `queue_policy.dart` next to `kDownloadConcurrency`, as pure functions. There is no setting.

| Stage | Limit | What it covers |
|---|---|---|
| Download | **D = 3** update jobs `running` at once, in a pool of their own | The transfer. Browse downloads keep the queue's own cap of two, so the worst case is five connections; six while a modal one-mod update's foreground download, which bypasses the cap, runs beside a run, which can happen from U4 until U7 moves that update onto the run. |
| Lookahead | **L = at most 3 archives or 1 GiB** ahead of the install, **always admitting at least one** | What the downloads may run ahead of the installs. See the definition below. |
| Unpack | **U = 1** at a time, and **at most one unpacked archive waiting** while an install runs | The unpack and the preview. With U = 1 and one waiting, the temp folder holds about two archives whatever the size of the run. |
| Install | **I = 1**, one chain for a run's writes and Browse installs | The write: snapshot, wipe, copy, put the patch back, link, record, and the prune of that write. |

D, L, U and I are the four numbers a changed verdict changes ([§4.5](#45-what-would-change-it)).
U and I are honoured by the policy functions, but `DownloadQueueHost` runs one loop per lane and awaits each job, so both are 1 whatever the constants say; raising either is a change to the host, with tests for two at once (U9).

**What the install chain serialises today** is a run's writes and Browse installs, and nothing else. The modal one-mod Update, a restore, a patch put in or taken out, Edit info and the library's own imports write a mods folder off the chain, each with its own prune where it has one, until U4 to U7 move the update paths onto it; a Browse install never prunes. Between a run's write and those, what protects a folder is the skip of a folder marked as being written (below), and whether prune needs a mutex is still open.

**Order.** The jobs start smallest first and largest last, by the file size the file lists on GameBanana, so the first mods are updated within seconds and a 1.2 GB file does not hold up the rest. The files of one press are all in line before any starts (`enqueueUpdates`), so the order holds whatever order the picks came in. A transfer that stalls ends at the stall timeout (never a total duration, [`downloads.md`](downloads.md) §5) and its job goes to the end of the line, so a degraded node costs only the job on it. The rows on the Updates page keep their order; only the order of work changes.
- **A stall sends a job to the end of the line once.** Its partial stays to resume from. A second stall of the same job fails it, as a transfer failure with Try again, rather than cycling a dead file through the line for as long as the run lasts. Try again sends a job to the end of the line too, and gives it its own stall to spare: being retried and having stalled are two flags (`deferred`, `stalled`).
- **A file that lists no size counts as 0** in the order and under the byte cap. Every file seen in the sampling of `gamebanana-api.md` §8 lists one.
- **The lookahead takes the line in order and stops at the first job it refuses**, rather than looking past it. The line is smallest first, so the only jobs behind a refused one that could fit are the ones sent to the end of it, a stalled or retried job; stopping keeps those from passing a large file, which then runs alone once nothing is ahead. A job held by its folder's pipeline (below) is passed over without stopping the line.
- **The unpack and install lanes take a job that has waited on a question first**, then the smaller, then the one asked for first. Between an update's write and a Browse install on the shared chain, one that waited goes first, then the one asked for first.

**What L counts.** An archive is ahead of the install from the moment its download starts until its install ends or its job is skipped, failed or removed. That covers a download still arriving, a landed archive, one being unpacked, an unpacked one waiting for the install, and one waiting on a question. L counts those jobs by number (at most 3) and by the size each file lists on GameBanana (at most 1 GiB together, 1024³ bytes, the job being admitted included), and a job is admitted to download only while both hold. A job held by its folder's pipeline is not counted (below). **One job is always admitted when none is ahead**, so a 1.2 GB file, which is over the byte cap on its own, runs once nothing else is ahead. "Nothing ahead" includes questions: a single unanswered question, even on a 5 MB job, keeps the 1.2 GB file out until it is answered or skipped, and since the line stops at the first job it refuses, every job sent to the end of the line waits behind it too; smaller files in front of it go on.
A job held by its folder's pipeline counts under L only while it waits on a question (a question keeps its place, §6); landed or unpacked and held, it does not. So after a Try again, the earlier job of a folder can wait for the answer to a question on a later job of the same folder before its download is admitted. The count of 3 and the download pool D = 3 coincide: when the installs lag, the downloads stop at three archives ahead, and the pool is never the limit that matters. The pure-policy tests of U3 pin the definition, including the always-admit-one rule and a 1.2 GB file after smaller ones.

**What the picture looks like.** Five mods of 20, 40, 80, 200 and 300 MB. The first three start downloading together (140 MB, three ahead). The 20 MB archive lands first and is unpacked while the other two arrive; its install starts while the 40 MB archive is unpacked and waits and the 80 MB one is still downloading. The 200 MB download starts only when the 20 MB install has ended and a place has opened, and the 300 MB one when the next has. At every moment at most three archives are between the start of their download and the end of their install, and one mod is installing. A 1.2 GB file in the same run is the last to be admitted and runs alone. The user sees one mod installing at a time and the others in their earlier phases.

**Rules no limit changes.** A layer is in one job at a time, and a second press for a layer already in a run adds nothing. **The run serialises each folder itself**: a folder has one write pipeline at a time, and the second job of a folder does not start its finish until the first has ended. A mod whose folder is marked as being written by something else (a restore, Edit info, a patch) is skipped at its write, with a reason on its row, and is not waited for, so an update never lands over a restore pressed while it queued. `whileWritingMod` is that mark and nothing more: a counter and a set of folder ids, read by the History buttons, the switch, the bulk actions and the update check. It blocks no second writer, and not every writer of a folder is shown to use it, so it cannot be the run's serialisation. A job that stops at a question leaves the unpack and install lanes and goes back in line ahead of the jobs that have not waited.
- **The pipeline is held from the download**, by the order the jobs were asked for: a job whose folder an earlier job of the run has not ended is passed over in line, holding no place, and is not unpacked or written either. A press asks for its bases before its patches (`enqueueUpdates`), so a base and its patch picked together are written base first, the patch's download starting once the base has ended. That costs the overlap of the patch's download with the base's write, and buys a pipeline that cannot deadlock.
  - Rejected: holding the pipeline only at the unpack or the write. The smaller patch would be admitted first, land, count under the lookahead and wait for its base; a 900 MB base and a 150 MB patch are then over 1 GiB together and the base is refused for good, and three such pairs fill the count cap the same way.
  - Rejected: not counting held jobs under the lookahead as the only rule. It lets every patch of a long run download ahead of its base, unbounded.
- **A held job takes no place.** A later job of a folder can still be past the line when an earlier one comes back: a failed base tried again while its patch is already unpacked, or a pick of an earlier job's file joining it. Such a job, landed or unpacked and waiting for its folder, counts neither under the lookahead nor as the one unpacked archive allowed to wait, since it cannot go on until the earlier job has and would otherwise hold the places that job needs. The earlier job is then unpacked and written first, so base before patch holds on Try again too. Held jobs arise only from those two acts of the user, so what they hold is bounded by them.
  The same two acts let the earlier job be unpacked and previewed while a later job of its folder is being written: its preview reads a folder mid-write. That is safe only because the install chain is one (I = 1), so the earlier job's own write starts after the later one has ended and previews the folder again then; a U9 that allows two writes must keep a folder's jobs from overlapping its unpack as well.
- **The skip is checked per folder, immediately before each folder's write**, and once by the host before the write stage starts, since the mark is set by a write rather than held by a lock. A job of several folders writes the ones that are free and leaves a marked one out with its reason, even one marked while an earlier folder of the same job was being written; a job whose every folder is marked is skipped.
- **One job per file.** A pick for a file an update job is still fetching, or that has landed and not been unpacked or waited on a question, joins that job. A pick for a file whose job has been unpacked or has waited, or that a Browse download is fetching, adds nothing: it could not join an unpack already made, and two transfers of one file share a `.part`.
- **What came of each mod.** A job that writes several folders ends with a result per mod: written, skipped with its reason, refused with its reason, or failed with its failure. A pick that joined by its file but that the archive's group does not list (nothing records a group, a repair, a patch layer) is refused, never dropped. The job's own outcome is failed when a mod failed, else updated when one was written, else refused or skipped; a row reads its own mod's result.

### 4.2 What is recommended, and what it rests on

The recommended default is the hybrid of the model above: three update downloads and a bounded lookahead, one unpack at a time with one waiting, and one install chain. It is a recommendation: the user has decided the mechanism (parameters held as constants, no setting, until measured) and has not yet confirmed these values ([§14](#14-decisions-settled-and-decisions-not-yet-confirmed)).

**The premises the model rests on.** The run has no per-mod confirmation, so the user is not the serial resource and the argument that one update at a time costs nothing, because a human answers each one in turn, does not apply. The only waits for the user are the questions of §6. The install service is not a singleton that has been shown unsafe to interleave: `downloads.md` §8 states that two installs would race on the `7z` run and on the mods folder, and for writes into existing folders that is stated and not shown ([§4.3](#43-stage-by-stage-what-the-code-allows-today)).

**Rejected alternatives.** One update at a time with only the next download overlapping the install keeps the network idle behind a degraded node, which is the one case where concurrency across different files pays. Several installs at once for different folders multiplies the half-written folders left by a close or a full disk, buys little on one disk, and rests on stages that are not shown safe. A user setting for the numbers adds a test and maintenance burden for values nobody has measured.

**The evidence**, from the code and from one session's sampling of GameBanana (`gamebanana-api.md` §8):
- **The only slow and unpredictable stage is the network.** A healthy GameBanana node serves 14 to 22 MB/s. Node assignment is deterministic per file, so a retry cannot leave a bad node, and four range connections to one file on a degraded node recovered only about 2 MB/s: more connections to one file do not help. A degraded node served 0.08 to 0.83 MB/s, up to about 25 minutes for 1.24 GB, and a node's speed swung tenfold within minutes. Only concurrency across different files routes around one bad node, and the queue's two slots exist for that.
- **Nothing above two concurrent transfers of different files has been measured**, and nothing on Windows. GameBanana publishes no limit; eight concurrent download starts all returned 206 and thirty concurrent API requests all returned 200. The figures are one session's sampling and are not settled properties of the service.
- **Install is disk-bound, and zip decode is single-threaded on the UI isolate**, so more installs and more unpacks buy little on one disk and multiply RAM and disk peaks. The sampled median archive is 21.9 MB, p90 95.7 MB and p99 358.9 MB, with a maximum of 1244.7 MB, so overlap matters for the large files and for degraded nodes.
- **Blast radius when unattended.** A killed app or a full disk leaves one half-written folder per install running, with nobody watching. One install at a time bounds that to one mod, and the safeguards of §4.4 are what make that one recoverable. Parallel installs would multiply what those safeguards bound: snapshots refused for space, unpacks counted against each other, writes the close guard waits for.
- **Practice elsewhere, from outside the repository and not verified here.** Package managers are reported to download in parallel and install in one locked transaction, and Vortex is reported to allow concurrent downloads and concurrent installs of different mods. None of it is evidence about GameBanana, and none says that installs of different mod folders are unsafe.

### 4.3 Stage by stage: what the code allows today

"Different folders" means two updates of two different mod folders.

**Safe to run concurrently today, by the code:**

| Stage | Why | Where |
|---|---|---|
| Download | Two transfers already run at once. The space check counts every transfer in flight. Only the cap, and the rule that an update's download bypasses it on the way in (`DownloadIntent.callerHandles`, `bypassesCap`), change. | `services/download/queue_policy.dart`, `download_service.dart` (`_requireSpaceFor`) |
| Unpack of a 7z or rar | Each call makes its own `zzz_archive_extract_*` directory and runs its own `7z` process (`Process.run`). | `services/archive_service.dart` |
| Preview | Read-only on the unpacked folders and the installed folder. | `UpdateApplier.preview`, `readFolderContents` |
| Snapshot capture | A unique directory per call and one group per mod uid; the sidecar write behind `uids.ensure` is locked per folder. A snapshot that will not fit is refused before it copies, with both figures as a typed value (`SnapshotNoRoom`), and a capture that fails part-way deletes the directory it made; a directory without a manifest is not listed, and a delete removes the manifest first. | `services/backup/snapshot_service.dart` (`take`, `_createSnapshotDir`, `_read`), `mod_uid.dart`, `lockSidecar` |
| The unpack's space check | It adds what every other unpack in flight still has to write, and the check and its registration run one at a time. An unpacked folder that waits is on the volume already, so the free space it reads has it taken off. | `services/unpacks_in_flight.dart`, `archive_service.dart` (`_spaceShortfall`) |
| `config.json` | Written to a temporary file and renamed over the old one, one save at a time, the last state asked for winning. | `services/config_service.dart` (`_saveToFile`) |
| Closing the app | Waits, at most 30 seconds, for the writes in flight that `whileWritingMod`, the library's imports, the record and prune after an update, a restore or a patch removal, an install's fill of the mod page's metadata, Update it's character change and the record that marks a new folder as a patch register, and never for downloads or questions. From the press on, no new write starts (`WritesInFlight.closing`), except a step of one already running. | `services/writes_in_flight.dart`, `main.dart` |
| Wipe and copy | Inside that mod's own folder only; one sequential stream per update (`copyDirectory` awaits each file). | `UpdateApplier._wipe`, `utils/directory_copy.dart` |
| The per-folder write mark and the rescan | `whileWritingMod` is a counter per folder id plus a set of the folders being written, so writes on different folders at once are counted separately. It marks and blocks nothing: a second writer on the same folder is not stopped, and not every writer is shown to use it, so the run serialises each folder itself ([§4.1](#41-the-model)). A rescan during a scan joins it and walks once more; an update check skips a folder whose write count moved. | `utils/state_providers.dart` |
| The shader record | Its read-modify-write is serialised, and a shader file the app did not place is never overwritten. | `ShaderFixesService._serialised` |
| Prune | By reading: a double delete degrades to a logged warning (`delete` checks `exists` and catches), and a snapshot mid-copy has no manifest yet, so prune does not see it and cannot delete it. A mutex on the chain, as `ShaderFixesService._serialised` is, costs a few lines. | `SnapshotService.prune`, `retention.dart` |

**Not safe, or not shown:**

| Stage | What is true | Where |
|---|---|---|
| Unpack of a zip | The whole archive is read into memory (`readAsBytes`) and decoded on the UI isolate (`ZipDecoder().decodeBytes`); there is no isolate or `compute` in the file. A second zip unpack gains no CPU and doubles the RAM. | `archive_service.dart` (`_extractZip`) |
| Closing past the bound | A write still running 30 seconds after the close is killed part-way, and the number killed is the number of installs running. Once closing begins the queue claims no install, no update write and no update unpack; it reads the closing flag itself, so a claim made from inside a tracked write is held back too. | `main.dart`, `DownloadQueue.claimNextForHost` |
| Installs of different folders through `ModManagerService` | `downloads.md` §8 states that two installs interleaving would race on the `7z` run and on the mods folder. It is stated and not shown for writes into existing folders; the stages above are folder-local and disjoint. What is not shown: the links in the game's mods folder and One at a time's turn-offs with two writes at once, the size budget of prune, which does not see a snapshot still being copied (the budget may be over by that snapshot's whole size until the next prune), and the library rescan landing on the right final list. | `services/mod_manager_service.dart` (`activateMod`, `deactivateMod`), `SnapshotService.prune` |
| Windows | The queue, the transfer beneath it, and a deactivate against a file the game holds open have never been run there. | `docs/downloads.md` §7, `docs/applying-updates.md` §7 ("Known gaps") |

Disk per active update is about twice the mod's size beyond the library: the archive in `<appData>/downloads` until it is consumed, the unpacked archive in the temp folder, a snapshot of the old folder in `<appData>/backups`, and the new files in the folder while the wipe has freed the old ones. They can be three volumes.

Tests that would show the unshown: two `UpdateApplier.apply` calls at once on two folders in one temp library (`test/support/temp_library.dart`), asserting both folders, both snapshots, both sidecars and the shader record; `prune()` started while a `take` of another mod is copying; two `activateMod` calls on different mods of one character with One at a time on; overlapping `whileWritingMod` calls (`test/support/held_write.dart`). A passing set is the licence for an install limit above one, and it still needs a Windows session.

### 4.4 What must be true before a run goes unwatched

A hands-off run is what makes each of these matter, and the run does not ship before they are built. Items 1 to 4 and 6 exist outside the run and are built ([§4.3](#43-stage-by-stage-what-the-code-allows-today)); item 5 is the run's own, and its engine is built with the lanes: the state and Continue and Cancel all. Its Error card and the "Stopped: <reason>" of the jobs it holds, in line, landed or unpacked, on the Updates row, the panel row and the deck card, are built; the Continue and Cancel all buttons are not, so nothing on screen sets a halted run going again, and a held job leaves only by its panel row's Cancel or Remove from queue.

1. **A snapshot space check.** A write that cannot be given a snapshot does not start, refused with both figures as a typed value (`SnapshotNoRoom`). A run's row and its card show both figures; the one-mod update window keeps its own failure text.
2. **A failed capture deletes the directory it made**, so no partial snapshot can be the newest of its mod.
3. **The unpack's space check counts the unpacks in flight**, not one unpack alone. The unpacked folders waiting (the one for the install and the ones that wait on a question) are not counted, because their bytes are on the volume already and the free space the check reads has them taken off; the run needs nothing more for them than to unpack through `ArchiveService.extractArchive`.
4. **A close guard.** Closing waits, bounded, for the write in flight, and never for downloads or questions. `downloads.md` §10 decided there is no "close anyway?" for a download, since closing loses only bytes that resume; a write killed part-way loses a folder.
5. **A halt on a disk-wide failure, reported on return.** A failure that every later job would share stops the run: not enough free space at the download, the unpack or the snapshot, a snapshot that cannot be taken, or a write that failed part-way. Jobs not yet written stay where they are, in line, landed or unpacked, with "Stopped: the disk is full" in place of their wait, and the run offers Continue and Cancel all; an Error card stays until closed, and the rows say what stopped. A failure of one mod's own (its file was removed, a password nobody gave) does not stop the others.
   - What halts: a download refused for space or one that could not write to disk; an unpack refused for space; a snapshot refused for space (`SnapshotNoRoom`) or one that could not be taken; a copy that failed after the clear; and a write stage that threw, since how far it got is not known. A stall, a removed file, a locked archive, an archive that is not one and a layout that cannot be reconciled are one mod's own.
   - The halt is set on every job of the run that has not ended (`DownloadJob.halt`), and each stage's gate reads it: a halted job is not admitted to download, unpacked or written. A transfer or an unpack already under way finishes and waits at the next gate, so nothing is cut off part-way. A job added while the run is halted, or tried again during it, is held by the same halt; a job takes its halt off when it ends, so one tried again after the halt is over is held by nothing. Continue clears the halt from every job of the list, ended ones included, and so does Cancel all, which ends the run it held.
6. **An atomic `config.json` write**: written to a temporary file in the same folder and renamed over the old one, and serialised.

### 4.5 What would change it

- Install time at least half the download time on an SSD, together with a clean test of two installs of different folders and a kill test: allow two installs for different folder ids, each folder keeping its own pipeline.
- One download stream far below the user's line: four update downloads.
- Three concurrent transfers throttled: back to two.
- Zip decode moved off the UI isolate: a second unpack lane.
- A Windows session that finds installs bound by something other than the disk (antivirus scanning is the suspect, and it is not measured): more install parallelism.
- Contention on a spinning disk: confirms one install.

A change of D or L is a change of a constant. A change of U or I is not: the host runs one loop per lane and waits for each job, so it has to run jobs side by side first, with tests for two at once (U9).

**The measurement.** A 10-mod run on the existing sequential engine with a timer on each stage (download, unpack and preview, snapshot, wipe and copy, link and prune, and the seconds a job waited for the previous stage) on an SSD and an HDD, and a test of three concurrent transfers of different files. The fallback, when the run cannot be done first, is to ship 3, 1 and 1 with each stage's seconds logged by the app (`logging.md`), so the first real runs are the measurement.

### 4.6 What the limits do to the surfaces

The design draws no new state for any of these numbers. Up to three rows read Downloading at once, each with its own mini bar and its own rate (with several transfers sharing a link each figure is lower and their sum is the link; the rate is shown per row only). The panel group's heading says "Updating", never "one download at a time". A waiting row reads "downloads next" for the first in line and "N ahead of it" for the rest; a job held by the lookahead cap reads "waits for an install to finish" while any job ahead of it is moving, and "waits for your answers" when every job ahead of it is waiting on a question, since nothing will free a place until the user answers. The deck's front card is the job that is furthest along (installing, then unpacking, then the furthest-along download, then the first queued, ties by run order, and last the jobs a halt holds, wherever they stopped) and "N more updating" counts the others, so the card reads the same for any limit. The board's front card ranks installing, then downloading, then the first active job and has no unpacking step; the order here wins, since an unpacking job is further along than a download.
A stalled transfer frees its slot and its job goes to the end of the line.

## 5. The surfaces

Every surface reads the jobs; none holds a copy.

**The Updates page row.** The Update and Ignore buttons give way to a status cell while the mod is in a run: a mini bar and the phase, and Answer, Try again or Undo beside the phase where one applies, as the board draws (the board's "Retry" is the app's "Try again"). A mod that is not in a run keeps its Update and Ignore. The page also lists the run's finished jobs ([§9](#9-what-stays-in-the-list)).

**The Downloads panel.** Needs your attention holds each question and each failed update with its two buttons, as the board draws; an update question's are Answer and Skip update, a failure's Try again and Remove from the list (the app's words for the board's "Retry" and "Remove"). A failed update row is in Needs your attention and not in Finished, which is where a failed download is today. An Updating group holds the live jobs in the order of work. Finished holds the jobs that ended, with Undo. The footer line while any update row is present reads "Each update keeps the file it replaces as a snapshot."; with none, the panel's footer is the downloads one. A waiting row is dimmed, with its size.

**The sidebar badge.** The Downloads row's amber pill counts the jobs that need an answer, as it counts waiting installs; the count of live jobs in plain mono and the red pill for failures follow the rules of `downloads.md` §14 unchanged, with update jobs counted among the live and failed ones. The Updates row's count follows the verdicts and drops the moment a write removes a mod's mark. The board counts questions and failures together in one amber pill; the app keeps amber for the jobs waiting on an answer and the red pill for failures, and that rule wins.

**The notification deck and cards.** Update jobs deal a Working card each into a deck of their own, so a run and a Browse download are two slots. The front card is the job that is furthest along (§4.6), titled "Updating <mod>" with the step as its body ("Downloading · 79 of 233 MB", "Unpacking", "Installing · replacing the files") and a 3px bar along its bottom edge for a download and for the write; "N more updating" is its last line. A job leaves the deck on its own, as a download does. Every job that has not ended has its card, in line or held by a halt included, and the deck is outside the stack's backstop of 20 cards: its Working cards are neither counted nor dropped, so a run of any length keeps its front card and every card behind it, and the Done, failure and halt cards beside it are not dropped to make room for them ([`notifications.md`](notifications.md) §7).
A finished update's Done cards are counted on one card: "<mod> updated" with a portrait for one, "3 mods updated" for several, with the names under it and the action Show, which opens the Downloads panel. An update whose file went on top of its mod as a patch replaced no file, so it is not counted there: it has a Done card of its own kind, "Patch added to <mod>" over "Your files stay, and you can take the patch out again from History.", counted as "Patch added to 2 mods" with the same Show. A failure is a card of its own, "Couldn't update <mod>", with Open Downloads, where the failed row offers Remove from the list; neither offers Try again yet, which is U8's. A question is the one Needs you card for every waiting update and install, with Answer (which opens the oldest question's window) and Open Downloads ([§6](#6-questions)). A halt ([§4.4](#44-what-must-be-true-before-a-run-goes-unwatched)) is one Error card that stays until closed, in place of the failure card of the one mod whose failure halted the run ([§10](#10-states-the-board-does-not-draw)).

**Three show and the rest fold.** The stack shows three slots and folds the rest into "+N more", oldest first ([`notifications.md`](notifications.md) §5). The deck is one slot, the Needs you card is one, the merged finished card is one, the merged patch-added card is one, and each failure is one, so a long run never fills the three by itself. The board folds the finished card first; the stack's own rule, oldest first, stands, since a merged finished card is raised newest each time and sits at the newest end, and a question or an error, which stay until closed, are the ones that can pile up.

**What each surface says about the finished row.** The row and the panel's Finished line say, in this order and only what is true: the outcome ("Updated", "Patch added" with where it went), "the 12 Aug file is a snapshot", the number of files dropped ("14 old files removed"), the number of hotkeys that changed ("2 hotkeys changed", opening a small list of before and after), the folders of the archive left out, and "left off: another was turned on" when One at a time turned the mod off during its write. The hotkey line is the only place the accepted loss of rebound keys becomes visible before the game.

## 6. Questions

A question is a decision the prepare cannot make. There are five.

| Question | Found by | Asked in |
|---|---|---|
| The archive's password | The unpack's own listing, before anything is written. | The archive password dialog ([`downloads.md`](downloads.md) §12), asked again when the password did not open the archive. |
| The layout is unknown (no recorded layout and more than one folder in the archive) or changed (a recorded layout the archive no longer matches). | The layout replay in the preview (`planUpdateLayout`). | The folders window in its Update context: what the mod has now, the archive's folders with hints, nothing ticked; the button names the mod. |
| The download is shaped like a patch. | The patch scan of the incoming folders. | The patch window in its Update context. |
| A patch is in the folder and nothing records which files are its. | The recorded patch files against the folder. | A small question: update anyway, which removes the patch from the folder while the saved copy keeps it, or skip. |
| A change at the write (below). | The write's own re-read. | The question it has become. |

**The patch question.** A patch-shaped download for a mod's base layer cannot go through the update's write, which clears the folder: `UpdateApplier._write` calls `_wipe` with no branch on whether the download is patch-shaped, so a patch-shaped file written as a base update leaves a folder that holds only the patch's files (and the recorded patch put back, which `test/update_applier_patch_shaped_wipe_test.dart` pins), while the confirmation window today says "Only its .ini files are being replaced — everything else here is left as it is". A run never writes a patch-shaped file by the wipe path. The window's two answers write it as a layer by placement (`applyPatchInto`, as a patch installed into a mod is written):
- **Put it on top of <the mod this update is for>**, preselected, "Your files stay and the patch goes on top, so you can take it out again from History."
- **Add it to a different mod you have**, with a library search and a ranked list, nothing picked, "The files it replaces are kept, so you can take the patch out again."

The preselected first answer departs from the rule that a suggestion is never preselected ([`patch-destinations.md`](patch-destinations.md) §3). The mod is not a guess: the user picked this file for this mod, so it is evidence, not a ranking. This is not yet confirmed by the user ([§14](#14-decisions-settled-and-decisions-not-yet-confirmed)). The "install it as a new mod" answer of the install-time window is absent here, since an update has a mod.
After "Patch added" the base layer would still list the same file as newer, since its recorded file is the old one; the run records a dismissal on the base layer, the value Ignore writes for that check (`UpdateCheck.dismissableUpTo`: the date of the newest of the newer files the check lists), so the row does not offer the update again. The value is read from the check when the press is made and carried on the job (`UpdateMod.dismissUpTo`), so a file list handed to the job that is not the check's own cannot dismiss more than Ignore would. It does not use `dismissalAfterTaking`, which writes the newest listed date only when a file newer than the one taken exists and returns null when the taken file is the newest listed, which is the common case here and would offer the same file again. The dismissal also silences any other file listed that is not newer than the newest, until something later is published.
The new patch layer is recorded as any write of a layer is: its page, its file at `exact`, the files it placed, and `dismissalAfterTaking` for the files listed above the pick, so a pick below the newest is not offered the newer file through the patch layer either.
`test/update_check_test.dart` ("a patch an update put on top of its own mod") settles what the verdicts of [`update-checks.md`](update-checks.md) §2 and §4 then say: the placed file is never offered to the base, since another layer of the folder records it; nothing the check listed is offered again; and a base file published after the dismissal is offered.
A patch added to a different mod writes a second folder: it is marked as being written for its duration, it records the layer on top, and that mod's session verdict is dropped, since it named the folder's old layers. The original mod is not written and keeps its update mark and its verdict, as a skip does: its row reads "Skipped · patch added to <mod>", with Update and Ignore beside it, and no dismissal is written on it.
When the different mod is another mod of the same job, the placement does not stand in for that mod's own update: a mod whose own file was written keeps "Updated" whatever the placement came to, and one whose own update was skipped stays skipped, keeps its verdict and its update mark, and has the patch on top.
A placement that finds nothing in the folder it goes into to match, or two places for a file (the install's `wrongMod` and `brokenMod` refusals), writes nothing, and the mod the update was for fails with "This file can't be written into this mod. Nothing was changed." (`UpdateModEnd.failed`, of the kind `refused`).
A patch-shaped file whose layout maps more than one of the archive's folders onto the mod is not asked about, since no answer could place it: the write refuses that mod with the same words (`UpdateModEnd.refused`), and nothing is written for it.

**The folders question** is the folders window in its Update context, the window an install's several folders open too. An update fills one mod that already exists, so there is nothing to name and no separate mods: the ticked folders replace what the mod has, together, and the mod keeps its name, its character and whether it is on. It shows what the mod has now (its folder, its first `.ini` and how many other files, the date of the file it holds, its size), and each folder of the archive with what it holds and its size. Nothing is ticked: a folder named like the mod's folder or a folder its record names is hinted "Same name as your folder", one named like the file "Named like the file", and one of images alone "Looks like preview images", and a hint ticks nothing. The button names the mod, "Update Pastel Burnice", and Skip this update is Skip. The one-mod update window asks the same window, with "Reinstall <mod>" for a reinstall.

**How questions queue.** A job that finds a question stops, keeps what it found, leaves the unpack and install lanes, and shows as Needs you. Several questions queue in the order they were found, and each one's Answer opens its own window; one window is open at a time, and after an answer the next is offered, not forced: the Needs you card counts down and its Answer opens the next. Answering runs the questions after it in the same sitting, as an install does: Pick folders is followed by the patch scan of that selection. The answer goes back in line for the lanes ahead of the jobs that have not waited, and a question the job comes back with within 20 seconds opens at once; one it finds later waits like any other, since a window opening long after the press would land over whatever the user went on to do. Those 20 seconds hold nothing back: the other questions can be answered meanwhile, and a question that comes back while another window is open waits for its own Answer. Closing a window without an answer leaves the question waiting; only Skip ends it.
An answer or a Skip counts only for the question its window was opened for (`UpdateWait.asking`): when that question was skipped or answered while the window was open, from its row or the panel, the answer or the Skip is dropped and nothing is said or logged.
A window opens only if its question still waits once what it shows has been read. For an update's question the one-window rule holds the window and not those reads, so the Answer of another update question pressed meanwhile opens its window. An install's question holds the rule from its press, its reads included, so an update's Answer pressed while an install's question is being read opens nothing, and that question waits for another Answer. The patch question also checks the rule before it ranks the library, so one pressed while another window is open reads nothing. The panel row's Update anyway opens no window, so its answer is stored even while another question's window is open.
An update's question is in hand from its press until its answer or its Skip is stored (a set keyed by the job and `UpdateWait.asking`, let go however the press ends: the window closed, an answer, a Skip, a read that throws, the job ending meanwhile). While it is, another press for the same question does nothing and says nothing: a second Answer, the Needs you card's Answer, Update anyway, or an earlier answer's same sitting reaching it. So a window the user closed is not opened again by an earlier press whose reads ended later, and a question whose Skip is still being stored opens no window. A press for another question goes through as above.
An answer is kept with the job's unpack, per mod (`UpdateRunKept.answers`), so the preview made again at the next unpack or at the write does not ask it again; a question the job did not have when it was answered (a verdict changed at the write) is still asked.
**A question is about one mod.** The wait names the mod (`UpdateWait.modId`), so only that mod's Updates row reads "Needs you · Answer" and the job's other mods read "Waiting to update". Skip on it skips that mod alone and the job goes on with the others, back through the unpack lane; that mod's row reads skipped at once, with its reason, and its Update and Ignore return. Skip on the password, which is about the archive, and on the folders question, which the job's first mod decides and whose preview drives the job, skips the whole job. Skip on a question about the job's last mod left ends the job there, each mod skipped with its own reason, so a mod skipped earlier as gone still says so. Only the user's own Skip is logged as a declined question; a skip for a reason the answer found is not.
Before a question's window opens, and before the unpack, the job reads again whether its mods' updates were ignored or written by something else meanwhile (§10, "Skip reasons"): such a mod asks nothing, its archive's password included, and a job with no mod left is skipped before it is unpacked. Its download is not stopped: the queue does not read sidecars, so a mod ignored while its file downloads still downloads.
The merged Needs you card's Answer opens the oldest question's window. Its Open Downloads button stays. An install's already-installed question has no window, so Answer on it opens the Downloads panel instead.

**A question can arrive while nobody is looking.** The downloads and unpacks run ahead of the installs, so a patch, a folders or a password question can be found on a mod far down the run, minutes after the user stopped watching. A waiting question holds its archive (a password) or its unpacked folders in the temp folder, and **it keeps its place under the lookahead cap**: it counts as downloaded and not installed. It does not hold the unpack lane or the one unpacked archive allowed to wait for the install, so the mods behind it go on, except a later job of its own folder, which waits for it in line ([§4.1](#41-the-model)). A single question already holds back a file larger than the byte cap, and every job sent to the end of the line behind it, until it is answered or skipped (§4.1, "What L counts"). The consequence is a bound: with the cap full of questions (three, or 1 GiB) no further download starts, the installs already unpacked finish, and the run waits for the user's answers with the Needs you card saying how many are waiting. The questions are bounded by the cap and never accumulate without limit, and the user finds at most that many on return.

**What state a mod is in while its question waits.** Nothing has been written. The mod's folder is untouched, its link is in place, and it is not marked as being written, since the mark is made at the write. The unpacked folders sit in the temp folder, which is memory on a tmpfs, and the unpack's space check does not add them, since their bytes are already off the free space it reads ([§4.4](#44-what-must-be-true-before-a-run-goes-unwatched)).

**Staleness at the write.** The preview was made at the unpack, and a question, or the wait for the install lane, may take hours. At the write the job re-reads the mod by its uid and previews against the folder as it is now: a rename, a restore or a deletion can have landed in between. A changed verdict is a new question; a folder that is gone is "the mod is no longer there" on its row, and nothing is written.

**A restart.** The queue is not persisted, so a restart loses every pending answer, every unpacked folder and the record of what a closed run had finished, and the session's verdicts, so the Updates page reads "not checked" until a check. The only residue is a `.part`, which resumes if the file is asked for again within 7 days. A run killed during a write is the case the close guard exists for ([§4.4](#44-what-must-be-true-before-a-run-goes-unwatched)); a run journal that would let a relaunch tell a half-written folder from a finished one is not designed here.

## 7. Failure, Try again, Skip, Remove from the list, Cancel

**One mod failing does not stop the others.** A failed job has its own reason, its own row and its own card, and the run goes on. The exception is a disk-wide failure, which halts the run ([§4.4](#44-what-must-be-true-before-a-run-goes-unwatched), item 5): the next job would fail the same way, and a nearly full disk is how a folder is left half written.

| Control | Means | Offered |
|---|---|---|
| Try again | Fetch the file again, at the end of the line. | On a transfer failure only. After a failure past the unpack or at the write there is nothing a second download would change. |
| Remove from the list | Take a failed row off the list. Nothing is undone; it is already over. | On a failed row. |
| Skip (update) | Write nothing and leave the mod's update mark, so the row says "Skipped, still on the 15 Jul file" and an Update button returns. It is not Ignore, which writes a dismissal and is the user's explicit act on the Updates page and in the update window ([`update-checks.md`](update-checks.md) §4). | On a question. A Skip that ends the job deletes what the job kept; a Skip of one mod while the job's others go on keeps the unpack for them ([§6](#6-questions)). |
| Cancel | A queued job leaves the line. A downloading job is cancelled and its partial deleted. A job that is unpacking or writing is not cancellable, as today. | A row the control applies to. |
| Cancel all | Does the above for every cancellable job in the run, all in one change so nothing is picked up on the way, and ends the run's halt. A job unpacked and waiting for the install lane, and one waiting on a question, are cancellable: what they hold is deleted and they leave. An unpack in flight is let finish and what it unpacked is deleted when it lands, never written; a write in flight finishes and its row says how it ended, and a failure of either halts nothing. | A run with more than one live job. |
| Continue | Start the jobs a halt left queued, once the user has made room. | On a halted run. |

**Closing the app** stops the run: downloads keep their `.part`, waiting jobs lose their answers, and the write in flight is waited for, bounded, by the close guard ([§4.4](#44-what-must-be-true-before-a-run-goes-unwatched)).

## 8. Undo

Undo is on a finished row (the Updates page and the panel); it is not on the card itself.

- **A base update's Undo is a restore of the snapshot the write took** (`restoreSnapshotFlow`): the mod's current folder is saved as a snapshot first, so undoing is itself undoable; the old files are copied back, the sidecar included, and what was added since is removed, "a file added by hand since the snapshot goes too". The record goes back to the old file, so the mod's tracking is as it was. The write removes the folder's update mark, so the job keeps the mark it removed and puts it back on Undo, as the Updates page's own Undo folds verdicts back.
- **A patch layer's Undo is Take out** (`removePatchFlow`), since the patch keeps its displaced originals in `.zzz-mod-manager/replaced/<id>/`. It takes its own snapshot first.
- **A sibling group** has one Undo per folder and no "undo all", since each folder has its own snapshot.
- **A mod switched off and on meanwhile:** the restore deactivates and reactivates as the update did and leaves the on or off state as it is.

**When Undo is not offered.** Undo shows while the job's own snapshot is still the newest snapshot of the mod, the mod's write counter has not moved since the job's write (`modWritesStartedProvider`), and the folder still exists under the same id. Otherwise the row reads plain "Updated" and History is the way. This is the safety rule: a restore removes files added since, so a restore after something else wrote would silently erase that. Undo shows only while the row is in the list.
Its unavailable state is drawn as the plain row, its failure as "Couldn't undo" with the reason (the snapshot was pruned, the folder was renamed, the folder is being written), and the merged "3 mods updated" card counts down to "2 mods updated" when one is undone.

## 9. What stays in the list

**The Updates row outlives its verdict.** The Newer files list is the mods whose check says there is a newer file, and a successful write removes that mark, so the row would leave the moment it reads "Updated · Undo". The page lists the run's jobs as rows in addition to the verdicts, until the user clears the finished ones. A skipped mod keeps its verdict and so its row. The sidebar's Updates count follows the verdicts and drops at once.

**Finished rows stay** until Clear finished or a restart, on the panel and on the page, since a row that left on its own would take the only record of a failure and the only Undo with it. A cancelled job leaves, as a cancelled download does; a skipped update and an undone one stay.

**Update N while a run is going** is allowed. The list counts the mods that are not already in the run and adds them to the line. The button is never disabled by a run.
A later press's jobs come after the earlier press's in the order asked for, so a folder's pipeline (§4.1) writes a patch picked in the earlier press before a base picked in the later one, the reverse of a single press's bases first. The base write puts the recorded patch back, so the folder comes out the same.

**A sibling group.** Picks that share an archive are one job. The run writes exactly the mods the user picked; a group member the user did not pick is not written and stays marked. A refusal is that mod's row with its reason: it is not what that folder is built on, its folders no longer match, or two mods claim one folder. A picked member already on the picked file is skipped as already updated rather than refused ([§10](#10-states-the-board-does-not-draw), "Skip reasons"), and a member written along with another mod of its archive is skipped at its own turn as already updated along with that mod.

**One mod and Reinstall are a run of one.** The one-mod Update window and the Updates row's, Browse's Update ready and the mod page's Update become a picker whose button enqueues one job and closes; Reinstall keeps its card, which is the consent for its standard facts, and enqueues a job of the kind `reinstall` that stops only for what the card could not say. The board's "1 mod" variant is the same picture with one row. One path remains in the modal flow: the base a dropped patch names (`installNamedBase`), which runs inside an install's finish with its own window and keeps it until it can wait on a job.

## 10. States the board does not draw

Each is specified here in the board's idiom: a row status in the status cell's colour for its kind, a panel row in the Needs your attention group (amber) or the Finished group, a card of the kind named, the same two-button shape. Nothing below needs a new component.

- **The archive's password.** Needs you, "The archive asks for a password. Authors usually put it in the mod description." with Enter password and Open mod page; after a wrong one "That password didn't open the archive." Row: "Needs you · Answer".
- **An unrecorded patch.** Needs you, "This folder holds a patch as well, and nothing records which files came from it. Updating removes the patch from the folder, and the saved copy keeps it." with Update anyway and Skip update. The update wipes the folder, so the patch leaves the live mod with the old version; the sentence says so rather than only that a copy has it. Card: the merged Needs you card.
- **An archive that expands to no folders** (`UpdateLayoutProblem.nothingToInstall`). A failed row, "The file has no mod folder in it. Nothing was changed.", with Remove from the list; no Try again, since the file is what it is.
- **A failure after the download.** "Couldn't unpack the file. It is kept in <folder>." (the archive stays, as an install's does) and "Couldn't save the old file as a snapshot. Nothing was changed.", each a failed row and an Error card with Remove from the list, and no Try again. The transfer reasons are the existing ones: stopped responding at 70 of 233 MB, couldn't reach GameBanana, not enough space (with both figures), the file was removed from GameBanana.
- **Failed part-way.** A copy that fails after the clear leaves the folder half old and half new. The row is amber-red: "The update stopped part-way. The folder is not as it was." with Restore, which is the snapshot restore without the Undo conditions, since this snapshot is the newest by construction. It is not "Nothing was changed", which is true only for a failure before the snapshot. It also halts the run.
- **A halted run.** The rows it holds, queued, landed or unpacked, read "Stopped: the disk is full" (or the reason that stopped it) in place of their wait; the panel's Updating heading gains Continue and Cancel all; one Error card, "Updates stopped", says which mod and why and stays until closed. The mod is the one whose failure halted the run: the mod whose snapshot or copy failed; when a write stage threw, the mod it was writing (`DownloadJob.writing`, the job's first when no folder had reported a step), a later mod of a shared archive's job included; and the job's first mod for a failure that covers the whole job, a transfer or an unpack refused for space. The card stands in for that one mod's failure card, and every other failed mod of the job has its own "Couldn't update <mod>" card, with the same reason when the failure covered the whole job.
- **Skip reasons**, each a Skipped row with its reason in place of "still on the 15 Jul file": "being changed by a restore", "no longer in the library", "ignored meanwhile", "already updated", "already updated along with <mod>", "its folder was renamed", "patch added to <mod>" (the file went into another mod as a patch, [§6](#6-questions)). The write re-reads each mod's verdict and its sidecar first, against what the press saw (the file the layer's record named and the dismissal it held): ignored meanwhile is a verdict that dismisses the layer, or a sidecar dismissal written or raised since the press that reaches the picked file's date, so a dismissal the user pressed Update over is not read as one; already updated is a layer whose record names the picked file, or names another file than at the press (a record that named none and names one now included) while the verdict neither offers the update nor dismisses it (a newer file through the one-mod window, so a job does not write the older file over it), and "along with <mod>" names the mod of another job of the run that wrote it. A layer whose record has not changed is written even with no verdict, since a base written earlier in the run drops the folder's whole verdict, its patch layer's included. A write by something else that starts after the write stage began reading, and so after the reads above, skips that folder as being changed, checked again at each folder's turn by the mod's write counter (`modWritesStartedProvider`), so an Ignore that lands between the read and the write is not erased by the write's own record.
- **Where a skip's reason is read.** No skip raises a card. The Downloads panel's Finished line reads a skip's reason only for a job skipped as a whole, and it is the reason of the job's first mod; the skip of a job's second or later mod, and a skip inside a job that also wrote or failed another mod, are not on the panel, whose line for each mod of a shared archive (below, "A shared archive") is not built yet. The Updates page lists a mod only while a verdict or the mark a run's write removed offers its update, so its row shows "still on the <date> file", "being changed", "patch added to <mod>", which keeps its verdict, and "along with <mod>", whose row the other job's removed mark keeps. A mod skipped at its question while its job goes on shows its reason at once, before the job ends, and keeps it however the job ends: its row stays skipped by the user when the stage fails, when the stage skips the job, when every folder is busy at the write, and when the stage finds the mod already updated or ignored meanwhile, and no failure card names it. An Ignore or an update through the update dialog takes the verdict, so "ignored meanwhile" and plain "already updated" reach the row only after a restore that brought back a sidecar dismissing or naming the picked file, since a restore leaves the session's verdict as it is. A mod gone from the library has no row, and a renamed one's row is under its new folder, which no job names.
- **A sibling group's refusals**, each a failed row: "not what this folder is built on", "its folders no longer match", "<mod> and <mod> claim one folder". A picked member whose layer is already current is not refused: the write-time check reads it as "already updated" and skips it (above).
- **A shared archive.** One panel row, with the archive's file, and under it "Updating 3 mods from this file", each mod with its own sub-line as its write comes; each mod's Updates row reads its own phase.
- **A job held by the lookahead cap.** The panel row, in the dimmed Waiting style, reads "<size> · waits for an install to finish" while any job ahead of it is moving, and "<size> · waits for your answers" when every job ahead of it is waiting on a question and nothing will free a place until the user answers. Both are told apart from "downloads next".
- **Undo unavailable or failing.** [§8](#8-undo).
- **Cancel all.** A ghost button at the right of the Updating group's heading, "Cancel all", shown with more than one live job. A write in flight is named "will finish".
- **A space warning.** Before a run starts, when the picked files' sizes plus a snapshot of the largest folder exceed the free space, the Update N footer says so in the amber notice style, "These updates may not fit: 2.1 GB needed, 1.4 GB free." It is a warning and does not disable the button, since exact numbers are not known before the unpack, where the real checks refuse.
- **The run's own line.** "2 of 3 updated" over the Updates page's list while a run is going, and Clear finished beside it once something has ended.
- **Copy and layout:** a speed placeholder in the first second, narrow widths (the status cell drops under the file line below 760px, as the row's buttons do), the light theme and Ukrainian lengths are checked when the rows are built, not drawn here.

## 11. Architecture

**The state is the queue's list of jobs**, with a new intent `DownloadIntent.update` (not `callerHandles`, no cap bypass) carrying an update task: the mod id, the layer, the picked file, the check's published list, the kind (update or reinstall) and the other picked mods of the same archive. Derived providers read it: the job of a mod (`updateJobOfModProvider`), which the Updates row reads, and a run summary (live, asking, done, failed; `updateRunSummaryProvider`), which the run's line reads for its Clear finished; the can-Undo predicate is U6's. The panel, the deck, the badge and the Needs you card read the jobs themselves.

**The work is done by `DownloadQueueHost`**, mounted above the page switcher and below the `Navigator`, which already drains installs, owns the cards and opens questions from its own context. It gains the update drain beside the install drain. Work that outlives a press is owned by the host and providers, never a page.

**The same three-part split as an install**, with the first part in its own lane:
1. `prepareUpdate`, in the unpack lane: unpack, extract, preview (the folder and the siblings), test each question without asking it, stop at the first that needs an answer.
2. `answerUpdateQuestion`, from the row or the card: the window from the host's context; closing keeps the job waiting; Skip declines.
3. `writeUpdate`, in the install lane: re-read the mod, re-preview, `whileWritingMod`, snapshot, wipe, copy, put the patch back, record, prune, the keybind diff into an update report, rescan once.
Neither half takes a `BuildContext`. They take the app's `ProviderContainer` and say nothing in words: what a failure is called belongs to the caller.

**Parts 1 and 3 exist** as `prepareUpdate` (`services/update_apply/update_prepare.dart`) and `writeUpdate` (`update_write.dart`). The modal flows call them, and so do the run's stages.
`prepareUpdate` unpacks, previews and returns what has to be answered as a value, never asking.
A password or a choice of the archive's folders stops it and it is called again with the answer, and the rest (a patch-shaped download, folders left out, a patch nothing records) are found together once the preview exists.
`writeUpdate` writes a base into the ticked folders or places a patch layer, and returns an `UpdateReport` holding what happened to each folder, the outcome it adds up to and the update marks it removed.
A patch write removes no marks and leaves the folder's verdict to the caller; the run's write stage drops it and keeps it in the report as the mark the write removed, as a base write keeps its own, so the Updates row reads the same before and after.
The sub-steps of §2 come from the applier's `onStep`.
`prepareUpdate` can also preview a kept unpack again without unpacking it (`unpacked:`), which is the re-preview at the write, and `writeUpdate` asks its `skipWhen` about each folder immediately before that folder's write, which is the run's per-folder skip.

**The run's engine exists, and Update N starts a run:**
- **The press.** `LibraryActions.updateMods` turns each pick of the list into an `UpdateEnqueue` (`updateEnqueueOf`: the mod's folder id, its uid and the layer the check named, the picked file and the published list) and hands the whole press to `enqueueUpdates` in one call; nothing is asked and no window opens. The press is logged as the consent (`update.run`). A mod's layer is always a `DownloadKey`, never null for the base, so a second press for the same layer is the same layer (`UpdateMod.sameLayerAs`) and adds nothing. The list and the button read `modsToUpdateProvider`, the mods with a file to install whose layer is not in a job that has not ended (`layersInRun`).
- **The jobs.** `DownloadIntent.update` and its `UpdateTask` (`services/download/update_job.dart`): the mods it writes, each a folder id, a layer, and the name and uid it had, the file its layer's record named (`heldFileId`) and the dismissal that record held (`heldDismissedUntil`) when the press was made, the one it is for first and the other picks of the same archive after it; the published list; the kind. The picked file is the job's own file. The job carries its question (`updateWait`, with the mod it is about), whether it has waited, whether it was sent to the end of the line and whether it has stalled, whether Cancel all reached it mid-stage (`stopOnSettle`), its skip reason, the halt holding it, the part of its write that has started (`writing`), the write's report and what came of each of its mods (`modResults`). The failures, skip reasons and questions are typed values; their words are in one place on screen (`screens/components/update_run_words.dart`), shared by the row, the panel and the cards.
- **The lanes.** D, L, U and I are constants in `queue_policy.dart` with pure functions for each (`updateAdmissions`, `lookaheadAdmits`, `updateLine`, `nextUpdateToUnpack`, `nextForInstallChain`, `folderPipelineFree`, `isHeldByPipeline`). One walk of the line says why each queued job is not started, its folder, the lookahead or the full pool (`updateHolds`), and both the admissions and a queued row's words read it, so a row never says "downloads next" for a job the lookahead holds. The queue claims through them: `claimNextUpdateUnpack` for the unpack lane, and `claimNextForHost` for the install chain, which hands out a Browse install or an update's write. Every settle of a stage admits what a place freed.
- **The queue's operations.** `enqueueUpdates` (one press, bases first, the second press for a layer refused, picks of one file joined), `settleUpdate` (a stage's result, what came of each mod, and the halt), `answerUpdate` (the seam U5's windows answer through), `skipUpdate` (the user's Skip, or with a reason the answer found), `markUndone`, `continueUpdates` and `cancelAllUpdates`; `clearFinished` leaves a failed update, which only `remove` takes. The derived providers are `updateRunSummaryProvider` and `updateJobOfModProvider`, which gives a mod's row its job and its own result. `DownloadJob.cancellable` is the one rule for what Cancel can stop, read by `cancel`, Cancel all and the row's buttons.
- **The host's drain.** `DownloadQueueHost` runs the unpack lane beside the install chain, through two seams, `updatePreparer` and `updateWriter`, whose production stages are `prepareUpdateJob` and `writeUpdateJob` (`services/update_apply/update_run_stages.dart`). The write stage checks that the unpacked folders are still there before anything is turned off and again just before the write, reads the mod again by its folder and uid with its origin from disk, skips the mods whose update was ignored or written by something else meanwhile (§10, "Skip reasons"), previews again against the folder as it is, and stops at a new question when the verdict changed. A mod no longer in the library is skipped as gone, one whose uid is now under another name as renamed. Both stages stop at a patch-shaped download or a patch nothing records for every mod the write would take, each picked mod of a shared archive from its own preview. A failure while it is still only reading is the job's own and halts nothing; a throw from the write itself halts the run.
- **What an ended job leaves on disk.** Its unpacked folders go when it ends, through `ArchiveService.deleteExtraction`, from the one list the stage's kept state gives (`HoldsUnpack`). Its archive goes too, whether it ended before its unpack (gone, renamed, refused, no library folder) or after, and so does one whose unpack was refused for lack of space, a failure that offers no Try again. The one archive kept is one the unpack failed on for any other reason (`UpdateFailureKind.unpackFailed`: a corrupt archive, no 7-Zip for a rar or 7z, a permission error), so the user can still unpack it by hand. A locked archive is not a failure: it is kept while its password question waits, and goes with Skip.
- **The timings.** The queue logs each update job's download, its waits for the unpack and the install lanes, and its unpack and preview; the write stage logs the write and each of its steps (snapshot, wipe and copy, link and prune), and only for a write that started: one where some folder reported its first step, whether it then ended or threw. A skip, a question at the write and a write whose every folder was left out at its turn are not timed as one. They are `update stage ended` lines under the `update` tag, so the first real runs are the measurement §4.5 asks for.
- **The questions the host asks.** The row's Answer, the panel row's own button and the Needs you card's Answer reach `DownloadQueueHost` through `downloadQuestionsProvider`, as an install's do.
  The password is asked in the archive password window and given back with `answerUpdate(password:)`, held for the one unpack it is given for.
  The folders are picked in the folders window in its update context (`pickUpdateFolders`, which the one-mod update asks too), from the archive's folders and the reason the layout asks, which the stage keeps with the unpack while the job waits (`UpdateRunKept.foldersQuestion`), and given back as `withPickedFolders`, so the archive is not unpacked twice.
  A patch-shaped download is answered in the patch window in its update context (`showUpdatePatchModal`), from what the stage keeps with the question (`UpdatePatchFinding`: the archive folders the layout maps onto the mod and what its `.ini` asks for that it does not carry) and the library ranked by those folders' names as a dropped patch's window ranks it (`preparePatchQuestion`), and given back as `PlaceAsPatch(intoModId)`.
  A patch nothing records is answered in a small window (`showUnrecordedPatchDialog`), or with the panel row's Update anyway directly, as `UpdateAnyway`.
  Each answer is kept per mod (`UpdateRunKept.withAnswer`), and the stages leave out the question it answers (`_answers`). Closing a window leaves the job waiting, and Skip (`skipUpdateQuestion`) ends the question, for the mod it is about or for the whole job.
  The queue numbers each time a job stops at a question (`UpdateWait.asking`), and `answerUpdate` and `skipUpdate` refuse an answer given to any other than the one the job waits on.
  Answer on a question whose mod has left the library, or whose update was ignored or written meanwhile (`modsLeftOut`, which also holds the mods skipped one at a time), opens nothing and skips that mod with the reason, the job's first mod as "no longer in the library" or "its folder was renamed", and the job's other mods as sharing a file that was not written.
- **The patch branch of the write.** A mod answered with `PlaceAsPatch` is not a target of the base write: after the bases, the write stage places its file into the folder it names (`placeUpdateAsPatch`, `update_write.dart`), through `UpdateApplier.applyPatchInto` under `whileWritingMod` of that folder, records the layer with `withAppliedPatch` as a patch installed into a mod is recorded (`PatchIdentity`), and, for the mod's own folder, the base layer's dismissal. The folder's session verdict is dropped, and the mod's own is kept in the report as the mark the write removed, so its row reads "Patch added"; a job whose every written mod was placed this way ends as `patchAdded`, and a patch put into another mod is that mod's skip, `UpdateSkipReason.patchAddedElsewhere` with `UpdateModResult.patchedInto`. A placement into another mod of the same job leaves that mod's own result as it was, and its verdict too when its own update was not written.
- **The surfaces.** The Updates page's row, the Downloads panel's Needs your attention, Updating and Finished groups, the sidebar badge and the cards read the jobs, as §5 says; how each is drawn is in [`library-screen.md`](library-screen.md) §17, [`downloads.md`](downloads.md) §9, §10, §13 and §14, and [`notifications.md`](notifications.md) §6. A job's phase is decided in one place (`updatePhaseOf`, `screens/components/update_run_words.dart`), with one rule for "Connecting..." (until the transfer is connected and its rate has a figure) and the halt read once, and each surface puts that phase into its own words there. The host tells a job's result once it has seen the job end, read a moment after the change that ended it, since a settle ends the job and then attaches what came of each mod in two steps.

**The report** (`UpdateReport`) is on the finished job: files written, dropped and restored, keybind changes, the snapshot id per folder, the mark the write removed (for Undo), the kind, and the folders of the archive left out. It is session state, like the verdicts.

**Seams for tests.** A stage seam, as `ArchiveInstaller` and `InstallQuestionAsker` are for installs, so the host's sequencing is tested without 7z, a mods folder or the network (`test/update_run_host_test.dart`). The lane policy is a pure function with tests for D in 1 to 4, the lookahead cap (including the always-admit-one rule), U and I, in `test/download/queue_policy_test.dart`. The queue's operations are in `test/download/update_run_queue_test.dart`. `prepareUpdate`, `writeUpdate` and the run's two stages run against real temp libraries (`test/update_run_stages_test.dart`), as `update_applier_test.dart` does.

## 14. Decisions settled and decisions not yet confirmed

### Settled by the user

A. **A run applies updates without a per-mod confirmation.** The press of Update N, the picked files and the footer text are the consent. The standard facts (a snapshot, the replaced contents, hand edits and rebound keys) are in the Update N and one-mod Update footers. The loss cases stop and ask (an unrecorded patch, a patch-shaped file, an unknown or changed layout, an archive password). The hotkey changes and the dropped files show on the finished row.
B. **Concurrency is built as parameters held as constants, with no setting, until measured.** What the numbers are is the recommendation in item 11 below.
C. **The update-run slices start now and the tracking window (`TrackingModal`) waits.** It is independent of them.
D. **The update deck keeps a Working card per job and is outside the notification stack's backstop**, so a long run drops none of its cards and the cards beside it are not dropped for them ([§5](#5-the-surfaces)).

### Taken from the recommendation, not yet confirmed by the user

1. **The patch question's default:** "Put it on top of this mod" preselected (the board's), nothing preselected in the other list, and a dismissal recorded on the base layer so the patch's file is not offered again ([§6](#6-questions)).
2. **What Undo does and for how long:** a snapshot restore for a base update, Take out for a patch layer, per mod, only while the job's snapshot is the newest and nothing else has written to the mod, and only while the row is in the list ([§8](#8-undo)).
3. **Needs you on the notification stack:** one merged card with an added Answer action, against the board's card per question ([§6](#6-questions)).
4. **One mod and Reinstall as a run of one**, everything except the base a dropped patch names ([§9](#9-what-stays-in-the-list)).
5. **An unrecorded patch stays a question**, with Update anyway and Skip.
6. **Update N while a run is going** is allowed, adds to the line and counts only mods not already in it.
7. **What Skip means:** it leaves the update mark, the row says so for the session and an Update button returns; it is not Ignore.
8. **Closing the app during a write:** closing waits, bounded, for a write in flight, and never for downloads or questions ([§4.4](#44-what-must-be-true-before-a-run-goes-unwatched)).
9. **How long finished rows stay:** until Clear finished or a restart, on the panel and on the page.
10. **Sibling members the user did not pick** are not written by the run and stay marked.
11. **The concurrency values** of [§4.1](#41-the-model): three update downloads in a pool of their own, a lookahead of at most three archives or 1 GiB (always admitting one), one unpack at a time with one unpacked archive waiting, one install chain for a run's writes and Browse installs, smallest first with a stalled file to the end, and a waiting question keeping its place under the cap. They are the recommended default, pending the user's confirmation.
12. **A halt on a disk-wide failure**, with Continue and Cancel all, reported by one Error card that stays ([§4.4](#44-what-must-be-true-before-a-run-goes-unwatched)).
13. **Update jobs are not pausable in the first build.** A download the user started from Browse can be paused; an update run has Cancel, and Pause is added only if wanted. The queue's `pausable` is false for the update intent ([§2](#2-the-phases-and-what-each-means-in-the-app)).
